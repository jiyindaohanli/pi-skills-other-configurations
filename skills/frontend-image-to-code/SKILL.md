# Frontend Image To Code

## 单一职责

把**用户提供的设计图**准确翻译成现有项目中的前端实现。

```text
设计图输入
→ 设计图解析
→ 可实现规格
→ 现有项目映射
→ 代码实现
→ 渲染对照
→ 视觉迭代
```

这个 Skill 只负责 image-to-code 闭环。它不负责凭空设计一套新页面，也不把通用项目规划、代码审查或独立的设计系统建设混进来。

## 工作契约

### 输入

- 用户提供的一张或多张设计图、截图、Figma 导出或局部参考图
- 目标项目和页面范围
- 已知的 viewport、设备、状态或交互要求
- 交互行为依据：Prototype、交互说明或状态流转标注；设计图未表达的行为以它们为准
- 设计标注来源：Figma/MasterGo/蓝湖等标注链接、标注截图、切图包或设计 token（如可提供）

如果用户没有说明项目路径，先确认当前工作目录和目标页面；不要在不知道落点的情况下开始修改代码。

### 输出

- 在目标项目中完成与参考图对应的页面或组件
- 保留项目原有技术栈、组件库、路由、状态和业务逻辑
- 对参考图对应的 viewport 或状态做渲染对照
- 记录已验证内容、实现假设和无法验证的部分

### 视觉源规则

1. 用户提供的设计图是唯一视觉事实源。
2. 设计图中的几何关系、层级、间距、颜色、字体层级、资产和状态优先于模型的默认审美。
3. 不生成另一套设计图来替代用户的设计图。
4. 设计图没有表达的内容，只补充维持功能所必需的最小实现，不擅自扩展成新的视觉方向。
5. 参考图有多个 viewport 或状态时，把它们视为同一设计的证据集合，而不是互相独立的页面。
6. 设计图未覆盖的状态（loading、空态、错误态、无权限、极端数据量），按设计已确立的语言做最小外推：复用同组件家族、间距节奏和色彩角色，不引入新的视觉方向；外推项进偏差清单并标为实现推断。

### 参考图优先级

多张参考图或图片与文字说明不一致时，按以下优先级判断：

1. 用户明确写出的尺寸、状态和交互要求
2. Figma 标注或设计稿中的明确规格
3. 原始高分辨率设计图
4. 同一页面的局部细节图
5. 低分辨率截图
6. 现有代码中的当前表现

现有代码主要用于确认功能和组件边界，不应自动覆盖设计图的视觉事实。无法判断是不同状态还是设计冲突时，先提问，不要擅自平均两套方案。

同一区域存在多版设计稿时，新版本优先于旧版本。收到改稿后做增量对照：只重做变更影响的区域及其相邻约束，已对照通过的部分保持不动。

### 多图一致性

多张图属于同一页面或同一产品时，统一提取并复用：

- 字体层级和行高逻辑
- 间距、圆角、边框和阴影规则
- 颜色角色和按钮层级
- 图标风格、图片处理和组件家族
- 响应式变化和状态命名

某一张局部图更清晰，只用于补充该区域的证据，不能让局部细节把整页的设计语言带偏。

### 规格获取

尺寸和规格证据按可信度从高到低使用：**设计标注 > 设计 token / 规范文档 > 高清原图测量（近似值）> 浏览器 bounding box 校正**。有标注时不目测近似。

如果图片分辨率不足以判断文字、间距、按钮或图标：

- 优先请求用户提供原始设计图或更清晰的局部图
- 如果已有本地原图，可临时放大或裁剪用于分析；这只是测量辅助，不是新的视觉源
- 保持原图的上下文，不能把临时裁剪误当成独立页面
- 没有更清晰证据时，把不确定项标为实现推断，不用通用模板替代

## 执行流程

### 1. 读取设计图和目标项目

先读取用户提供的图片。记录：

- 图片像素尺寸和可能对应的 viewport
- 图片包含的页面、组件或状态
- 图片是完整页面、局部区域、多个状态还是多个响应式视图
- 图片中哪些文字、图标、图片和数据是真实内容，哪些可能只是占位

再读取目标项目中与页面有关的最小必要范围：

- `package.json`、锁文件和实际可用脚本
- 路由入口、目标页面和父级布局
- 目标组件及其直接依赖
- 已有的 CSS/SCSS、主题变量、设计 token、图标和资源
- 当前使用的组件库和版本 API

不要为了 image-to-code 任务扫描整个仓库，也不要先安装新的框架、组件库或浏览器工具。

完成标准：知道参考图对应哪个页面/组件、目标代码入口在哪里、使用什么技术栈以及哪些现有结构必须保留。

### 2. 建立设计图规格

在编辑代码前，按从外到内的顺序解析图片。

#### 画布和区域

- 页面背景、主容器、最大宽度和左右边距
- header、导航、侧栏、主体、底部和固定区域
- 区域之间的对齐轴、分栏比例、间距和滚动关系
- 元素的宽高、最小/最大约束、定位方式和层叠顺序

#### 视觉系统

- 背景、表面、边框、分割线、阴影、圆角和遮罩
- 字体家族线索、字号层级、字重、行高、颜色和截断
- 图标尺寸、对齐方式、按钮命中区域和状态差异
- 图片、渐变、纹理和其他真实资产的使用方式

#### 行为和状态

- 活动、悬停、聚焦、禁用、展开、收起、选中和清除
- 单项/多项、空数据、长文本、溢出、滚动和窄屏
- 哪些元素是固定的，哪些随容器或内容变化
- 设计图明确给出的数值约束，例如固定宽度、遮罩尺寸或安全边距

#### 规格记录

在动手前形成一份紧凑的设计规格，至少包含：

```text
区域：位置 / 宽高关系 / 对齐轴 / 滚动或固定方式
视觉：背景 / 边框 / 圆角 / 阴影 / 字体层级 / 颜色
内容：文字 / 图标 / 图片 / 截断 / 内容长度敏感点
状态：当前状态 / 可见变化 / 触发方式 / 行为结果 / 相邻区域影响
证据：设计事实 / 项目事实 / 实现推断 / 置信度
```

尺寸分析优先使用相对关系和 viewport 比例。图片里的像素值只有在已知原始 viewport、设计标注或明确设计规格时才直接当作 CSS 像素；否则按近似值记录，并按上面的证据链逐步校正。

#### 资产和文字

- 先在项目资源目录中按文件名、尺寸、图标名称和现有引用寻找对应资产
- 参考图中可辨识的文字优先原样实现，不用泛化文案替代
- 不用随机图片、远程占位图或临时图标掩盖缺失资产；确实缺失时记录替代方案
- 组件库图标只有在形状、尺寸和语义都匹配时才替代设计图中的图标
- 图中的静态文案按真实业务约束落地：布局不锁死单语种文案长度，按钮和操作按项目权限体系控制显隐，示例数据映射到真实字段

把结论分成三类：

- **设计事实**：可以从图片直接观察或测量
- **项目事实**：可以从现有代码、组件 API 或配置确认
- **实现推断**：图片没有明确表达，但代码必须做出的选择

只在图片和项目代码无法共同确定结构时提问。可用结构化提问工具就使用它；没有时直接在对话中问一个最小问题。不要为了颜色、间距等已经可以从图中判断的细节反复询问。

完成标准：有一份足以指导实现的规格，主要几何关系、视觉层级和目标状态都已明确。

### 3. 把设计图映射到现有代码

先建立映射表：

```text
参考图区域 → 现有页面/组件 → 需要修改的样式或状态 → 验证方式
```

映射完成后，先写出实现顺序和视觉风险最高的三个区域。通常优先处理：

- 页面主容器和父级布局
- 设计图中最有辨识度的 header、导航、标签、表格或主体区域
- 影响多个组件的固定区、滚动区、遮罩和 z-index

每个区域都要能回答“参考图中的什么证据对应到代码中的什么位置”。如果无法建立映射，先补充项目侦察或提问，不直接开始堆 CSS。

映射时遵守：

- 优先复用现有组件和主题变量
- 先找已有的同类组件，再决定是否新增组件
- 把布局责任放在正确的父级，不用局部绝对定位掩盖父级尺寸问题
- 不因还原一张图片而重写路由、状态管理、API、权限或数据流
- 不为了视觉效果引入项目中不存在的 CSS 框架、动画库或组件库

对于常见项目的适配重点：

- **Vue / Vue 3**：检查 SFC、`scoped` 样式、响应式数据、slot、Teleport 和父级布局。
- **Element Plus / Avue / ant-design-vue**：先确认项目已有封装和主题变量，再处理组件库默认 padding、line-height、z-index、弹层挂载和状态样式。
- **uni-app**：确认目标平台、页面生命周期、单位体系、安全区域、原生组件限制和多端样式差异。
- **React、Svelte、Angular 或原生前端**：遵循各自已有的组件、状态、样式和构建约定，不把上面的框架假设带入。

这些是适配策略，不是技术栈限制。

### 4. 实现设计图对应状态

按下面顺序编码，减少视觉偏差的传播：

1. 页面和区域几何：容器、宽高、分栏、对齐、滚动和定位
2. 视觉 token：背景、边框、颜色、字体、圆角、阴影和图标
3. 内容尺寸：真实文字、长文本、图片比例和截断规则
4. 状态与交互：活动、悬停、聚焦、禁用、清除、展开和溢出
5. 响应式：只实现设计图表达的 viewport，或为保持布局可用补充必要断点
6. 动效：只实现设计图或现有产品明确需要的动效

实现过程中保留“原图 → 代码”的对应关系：

- 不把有辨识度的区域改写成通用模板
- 不因实现方便而压缩原图的留白、间距或文字层级
- 不把多个不同区域合并成重复的卡片/栅格结构
- 不用随机资产、泛化文案或默认组件样式替代可识别的设计细节
- 保留控件语义、键盘可达性、既有权限判断和业务状态；视觉差异用样式解决，不用删减交互解决
- 每完成一个高风险区域，就用规格表检查一次几何关系和视觉优先级

每完成一层就检查它是否破坏了上一层的几何关系。不要先堆叠装饰，再用大量负 margin 或绝对定位修正布局。

如果参考图只展示一个状态，不要借机设计完整的新产品；但要保证图中的按钮、标签、菜单或输入等已有交互不会被做成静态假图。

### 5. 渲染、对照和迭代

代码完成后，使用项目已有的启动、构建或预览方式渲染页面。

优先使用当前环境可用的浏览器自动化、E2E、截图或组件测试能力。对照开始前固定变量：viewport 与 DPR、字体加载完成、locale、用户权限、mock 数据、动画/过渡关闭，先消除环境差异再判断视觉差异。

对照手段按用途与诊断顺序选择：半透明叠加看几何偏移，playwright/pixelmatch 等像素 diff 量化差异，DOM/bounding box 定位布局原因，computed style 定位 CSS 来源。没有专用浏览器工具时，可以使用：

- 项目已有的预览或 E2E 脚本
- 真实构建结果配合静态 harness
- 明确记录无法完成浏览器渲染的原因

不要把缺少某个工具当成不适用，也不要在没有运行结果时声称已经完成像素级验证。

对照时按以下顺序修正：

1. 画布尺寸、整体比例和主要对齐轴
2. header、侧栏、主体、固定区和滚动区的几何关系
3. 关键元素的宽高、间距、边界、背景和遮罩
4. 文字层级、截断、图标和颜色
5. 参考图表达的交互状态和响应式状态

采用分层对照，而不是一次性凭感觉微调：

- **几何层**：画布比例、容器、分栏、对齐轴、固定区、滚动区和主要宽高
- **视觉层**：背景、边界、颜色、字体层级、图标、按钮、圆角和阴影
- **状态层**：活动、悬停、聚焦、溢出、长文本、窄屏和内容数量变化

每轮只优先修正当前层级中影响最大的差异。修正父级布局后重新观察子组件，不用局部偏移掩盖父级错误。达到主要几何、视觉层级和目标状态一致后停止迭代；没有实际像素 diff 时，不宣称像素级一致。

对照以设计图与同 viewport 的渲染截图为一对进行；对照结论写入交付报告，临时截图与探针不保留。

至少对照参考图对应的 viewport。参考图包含多个 viewport 或状态时，逐个对照。对于标签栏、列表、表格、弹层等内容驱动区域，额外检查最小内容、长内容、溢出和相邻固定控件，防止只在示例数据下成立。

视觉差异较大时，回到规格和父级布局重新定位问题，不要通过局部随机微调掩盖结构错误。连续两轮主要差异未缩小时停止微调，报告剩余差异与原因，不进入无限打磨。

## 完成标准

只有满足以下条件，才报告 image-to-code 完成：

- 参考图中的主要区域、几何关系和视觉层级已经在目标项目中实现
- 使用了项目现有的技术栈、组件约定和资源路径
- 参考图中的真实内容或尺寸敏感内容没有被随意替换
- 图中可见的交互状态已经实现，必要的长文本、溢出或响应式行为没有破坏布局
- 已用可用的方式完成至少一次渲染对照；无法渲染时说明原因和替代检查
- 与设计稿不一致的位置已列入还原差异清单；设计未覆盖状态的外推已标注为实现推断
- 已运行与本次改动相关的 lint、typecheck、build 或测试脚本
- 临时 harness、截图、探针和日志已经清理，除非用户要求保留

## 交付报告

最终只报告与本次 image-to-code 任务有关的内容：

- 修改的文件和对应的设计区域
- 参考图中已还原的状态和 viewport
- 使用的渲染/截图/DOM/构建检查
- 尚未验证的内容及原因
- 仍然存在的实现推断
- 还原差异清单：与设计稿不一致的位置、原因（组件库约束 / 交互合理性 / 技术限制 / 设计未覆盖）以及是否需要设计确认
